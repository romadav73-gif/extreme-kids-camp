# Growth OS 6.5 — исправление доступа и синхронизации

Это доработка существующей 6.5, а не новая система SMM или отдельный кабинет Софы. В `source/` закреплён прежний интерфейс. Сборка заменяет его небезопасный запуск и передачу всей базы новым серверным API.

## Что изменено

Роль, сотрудник и рабочая база определяются только серверной учётной записью. Параметры `r`, `w`, `m`, `p` в ссылке не являются полномочиями. Сервер выдаёт каждому сотруднику разрешённые записи и проверяет каждое изменение. Зарплата другого наставника, продажи другого администратора и неразрешённые записи не попадают в ответ.

Вместо общих ключей — персональные пароли scrypt, случайные сеансы в HttpOnly/Secure/SameSite cookies, одноразовые приглашения и отзыв сеансов. Защищены Origin/CSRF, опасные пути и ссылки; настроены CSP, запрет встраивания и кеширования ответов. Локальные черновики шифруются отдельным ключом пользователя, который не хранится в localStorage.

Обмен — изменение конкретных полей с проверкой прежнего значения, транзакцией PostgreSQL и идемпотентным идентификатором запроса. Независимые изменения сохраняются вместе; конфликт одного поля требует выбора пользователя. Повтор запроса после потерянного ответа не создаёт дубликат. Удалённые идентификаторы защищены от автоматического восстановления. Нет общедоступного сброса или загрузки произвольной базы из браузера.

## Проверки

`npm test` запускает серверные проверки. При `TEST_DATABASE_URL` используется настоящая PostgreSQL, иначе тестовый MemoryStore. Разрушающие тесты допускают только базу с именем `ek65_test`. `node tests/e2e.cjs` выполняет настоящие браузерные сценарии входа, вкладок, форм, мобильной компоновки и обмена.

GitHub Actions использует отдельный контейнер PostgreSQL 18, Chrome и только искусственные данные. Результаты и точные исходники сохраняются артефактом. Ошибки завершают проверку с ненулевым кодом. Тестовый пароль в `tests/` не является рабочей учётной записью и никогда не создаётся production-функцией.

## Запуск

Нужны Node.js 22+, PostgreSQL и переменные из `.env.example`. `DATABASE_URL` и `SECURITY_KEY` задаются только в защищённых настройках сервера. `SECURITY_KEY` — криптографически случайный секрет не короче 32 байт; его необходимо резервировать: он используется для журнала и ключей черновиков. Соединение с БД проверяет TLS-сертификат. При частном корневом сертификате укажите `DATABASE_CA_PEM`, а не отключайте проверку.

```
npm install
npm run build
NODE_ENV=production npm start
```

Для Vercel корень проекта — `secure-growth65`, сборка `npm run build`. `vercel.json` направляет запросы в серверную функцию с явным перечнем доступных файлов. Без настроенной базы production закрывается с 503; небезопасного перехода в MemoryStore или MantleDB нет.

## Безопасный перенос

До переключения необходимо сохранить экспорты с устройств Романа и Софы, включая локальные несинхронизированные изменения, согласовать единую копию и временно остановить редактирование старой версии. Не очищать localStorage старого сайта.

Сначала только проверка:

```
node scripts/import.cjs inspect --file /private/club-export.json
```

Она сообщает SHA-256, количества записей, ошибки и возможные дубли. Ничего не удаляет и не исправляет автоматически. Импорт разрешён только после устранения противоречий, с точным SHA и явным подтверждением остановки изменений:

```
node scripts/import.cjs import --file /private/club-export.json --expected-sha256 SHA_FROM_INSPECT --freeze-confirmed --username roman --out-dir /private/ek65-migration
```

Команда отказывается заменять уже настроенную серверную базу, создаёт закрытую резервную копию, сверяет обратное чтение и сохраняет одночасовое приглашение собственнику в приватный файл, не в журнал. Удаление старой базы в эту команду НЕ входит.

После проверки новой базы нужно отдельно прекратить использование старых ссылок и закрыть старое хранилище. Один новый защищённый интерфейс не отзывает общий ключ прежней MantleDB. До подтверждённого переноса и проверки резервной копии удалять старое хранилище нельзя.

## Границы и обязательные условия выпуска

Это компактная серверная модель для одного клуба: приватная строка JSONB блокируется транзакцией `SELECT ... FOR UPDATE`. Она обеспечивает последовательность операций, но не рассчитана на неограниченный рост; рабочая база ограничена 2,5 МБ. При увеличении нагрузки требуется нормализация таблиц, а не повышение лимитов наугад. Авторизация реализована в серверном API; RLS не выдаёт права сотрудникам напрямую.

Пройдённый CI не означает, что production уже переключён. Нужны отдельная рабочая БД, безопасные секреты, проверенная миграция, подтверждение матрицы прав, тесты на опубликованном адресе и план отката. Автоматического production-deploy здесь нет. MFA и внешняя независимая проверка не реализованы этим изменением.
